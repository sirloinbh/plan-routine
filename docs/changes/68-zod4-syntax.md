# #68 백엔드 검증 코드를 zod 4 문법으로 옮기기

- 이슈: [#68](https://github.com/sirloinbh/plan-routine/issues/68)
- 브랜치: `chore/68-zod4-syntax`

## 목적

중앙 `sirloinbh/project-standards#386`의 1단계다. 중앙이 `zod`를 4.6.7로 올릴 때 이 앱이 깨지지 않도록 코드를 먼저 옮긴다. 보안 권고 GHSA-mrhx-c7xc-m3w5의 Dependabot 알림은 그 동기화로 닫힌다. 이 PR만으로는 닫히지 않는다.

## 변경 — 2026-11-01

- `backend/src`의 8개 파일이 `zod/v4`에서 불러온다. 설치된 3.25.76에 이 경로가 들어 있어 `package.json`과 잠금 파일은 바꾸지 않았다.
- `required_error`, `invalid_type_error`, `errorMap`을 `error`로 옮겼다.
- 문자열과 회고 배열 최소 개수의 `.min()`, `.max()`를 `.refine()`으로 바꿨다. zod 4의 길이 검사는 `.length`가 있는 입력이면 타입 실패 뒤에도 돌아, 배열이나 빈 문자열을 잘못 보내면 메시지가 두 개가 된다.
- 회고 배열에 `.max(1000)`을 새로 넣었다. 이 배열은 길이 제한이 없어 `standards:check`가 경고하고 있었고, 원소마다 오류가 쌓이는 보안 권고(GHSA-mrhx-c7xc-m3w5)의 대상이었다. 4.6.7은 앞쪽에 연속된 길이 검사만 원소를 읽기 전 거절에 쓰므로 `.max()`를 체인 맨 앞에 둔다. 목표 개수에 앱 제한이 없어, 실제 기간에서 나오기 어려운 값으로 정했다.

## 바뀌는 응답

전환 전, 3.25.76의 `zod/v4`, 4.6.7을 같은 입력 1136개로 실제 라우트에 보내 상태 코드, 응답 본문, DB에 넘기는 값을 비교했다. 전환 전과 10개가 다르다. 저장되는 값이 바뀌는 경우는 없다.

| 입력                                                             | 전                                    | 후                                                                      |
| ---------------------------------------------------------------- | ------------------------------------- | ----------------------------------------------------------------------- |
| 본문이 배열(루틴 등록, 이름 변경, 이동, 일기 저장)               | `Expected object, received array`     | `Invalid input: expected object, received array`                        |
| 회고에서 같은 목표를 두 번 보내고 메모도 잘못됨                  | 메모 메시지만                         | 메모 메시지 뒤에 `같은 목표를 두 번 회고할 수 없습니다` 추가            |
| 회고 1001개 이상, 모두 올바르고 목표가 다름                      | 검증 통과(시험에서는 없는 목표라 404) | 400 `한 번에 회고할 수 있는 목표는 1000개까지입니다`                    |
| 회고 1001개 이상, 원소가 잘못되거나 목표가 겹침                  | 400, 원소 오류 또는 중복 메시지       | 400, 4.6.7에서는 제한 메시지만, 3.25.76에서는 제한 메시지와 기존 메시지 |
| `reviews`가 1001자 이상 문자열이거나 `length`가 1001 이상인 객체 | `회고할 목표가 없습니다`              | 뒤에 제한 메시지 추가                                                   |

3.25.76과 4.6.7은 넷째 줄의 2개만 다르다. 4.6.7은 원소를 읽기 전에 거절한다. 배열 본문과 메모 메시지 차이는 요청을 직접 만들 때만 나오는 입력으로 보고, 400이 유지되어 고치지 않았다. 다섯째 줄은 맨 앞의 `.max()`가 빠른 거절에 필요해 남겼다. 코드 포인트 계산 차이를 막기 위해 넣은 이모지 입력은 차이가 없었다.

`z.record`는 쓰지 않는다. 본문의 `constructor` 키가 null, 숫자, 객체인 입력은 전후 응답이 같고 500이 나지 않는다.

## 검증

- `npm run check`: 통과(백엔드 91개 중 77개 통과, 14개 건너뜀, 프론트엔드 235개 통과, 2개 건너뜀, 스킬 4개 통과). `TEST_DATABASE_URL`을 비워 DB 통합 테스트는 로컬에서 돌리지 않았고 PR CI로 확인한다.
- 4.6.7: `knip`이 함께 설치한 사본으로 타입 검사, 백엔드 단위 테스트, 전후 비교를 통과했다. 설치 자체의 확인은 중앙 동기화 PR의 CI로 한다.
- 한 번은 `saving trims the text...` 테스트가 `fetch failed: bad port`로 실패했다. 테스트 서버가 받은 임의 포트가 fetch가 막는 포트였던 경우로 코드와 관계없고, 다시 돌리니 통과했다.
