# #19 하루 루틴 수정·보관 후 키보드 포커스 복귀

- 이슈: [#19](https://github.com/sirloinbh/plan-routine/issues/19)
- 브랜치: `fix/19-routine-focus`
- 일자: 2026-11-01 (Asia/Seoul)

## 목적

저장·취소·보관·이동 뒤 눌렀던 요소가 다시 그려지거나 비활성화되면서 키보드 포커스가 `body`로 빠졌다. 키보드와 화면 낭독기 사용자가 위치를 잃지 않게 한다.

## 변경

`frontend/src/use-routine-list.ts`, `routine-list.tsx`. 항목 관리 부품을 함께 쓰는 하루·주간·4주·12주 화면에 모두 적용된다.

| 동작                | 포커스가 가는 곳                                                          |
| ------------------- | ------------------------------------------------------------------------- |
| 이름 수정 저장·취소 | 그 루틴의 "수정" 버튼                                                     |
| 이름 수정 실패      | 입력칸(루틴이 사라졌으면 옮기지 않는다)                                   |
| 위로·아래로         | 같은 버튼. 끝에 닿아 비활성화되면 반대쪽 버튼                             |
| 보관 확인           | 다음 항목의 "수정". 없으면 이전 항목, 그것도 없으면 그 카드의 추가 입력칸 |
| 추가                | 그 카드의 추가 입력칸                                                     |

- 다시 불러오기가 끝난 뒤에 포커스를 옮긴다. 행의 순서가 바뀌면 버튼의 위치도 바뀌기 때문이다.
- 다른 곳의 변경을 반영하는 다시 불러오기는 포커스를 옮기지 않는다.

## 테스트

`frontend/src/routines.test.tsx`: 위 표의 각 동작, 다른 곳에서 보관된 루틴의 수정 실패, 화면 복귀 때 포커스 유지.

## 검증

- 로컬(`TEST_DATABASE_URL` 제거): 포맷·lint·타입 검사·빌드 통과. 프론트엔드 테스트는 `--testTimeout=60000`으로 197개 중 195 pass / 0 fail / 2 skip이다(skip은 #7 기록과 같은 다크 모드 전용 공통 테스트). 백엔드는 바뀌지 않았다.
- 브라우저: 임시 API에 Vite 개발 서버를 연결하고 헤드리스 Chrome(PC 1440×900)에서 실제 Enter·Tab 키 입력으로 포커스 위치를 확인했다. 콘솔 오류는 없었다. 수정 저장·취소, 위로 이동, 추가, 보관 확인을 확인했다. 화면 모양은 바뀌지 않아 모바일은 따로 확인하지 않았다. 실제 화면 낭독기로는 확인하지 못했다.
